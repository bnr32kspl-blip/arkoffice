# ローカル LLM ランタイム仕様

| 項目 | 内容 |
| ---- | ---- |
| 文書 ID | `ARKOFFICE-SPEC-LLM-001` |
| 状態 | 実装済み（L1–L6 / Windows x64） |
| 対象 OS（本フェーズ） | Windows x64 |
| macOS | 枠のみ（後続フェーズ。Metal 想定） |
| 関連 | [閉域展開](air-gapped-deployment.md)、[許可リスト](network-allowlist.md)、[検証リスト](verification-checklist.md) |

本仕様は、ArkOffice に同梱する `llama-server`（llama.cpp）と、GGUF の別配布、ローカル／リモート推論の選択、GPU バックエンド、リクエスト待ち表示について定義する。

---

## 1. 目的と非目的

### 1.1 目的

- エンドユーザーが **Node / 手動 llama インストールなし**でローカル AI を使えること
- 調達スペックに応じ、次の **2 モード**を選択できること
  1. **ローカルモード**: 同梱 `llama-server` ＋ 既定フォルダの GGUF
  2. **リモートモード**: 同一 LAN 上の推論 PC の OpenAI 互換 API（`http://host:8080/v1` 等）
- dGPU / iGPU / CPU に応じて **CUDA / Vulkan / CPU** を選べること（自動検出＋手動上書き）
- 推論サーバへ複数リクエストが集中しても、**順番待ちと待ち状況の表示**ができること

### 1.2 非目的（本仕様の範囲外）

- GGUF モデルファイルのアプリ同梱・自動ダウンロード
- GPU ドライバのインストール
- Inno Setup への移行（別途インストーラ簡素化で扱う）
- 本格的な優先度付きジョブスケジューラ／管理者ダッシュボード（将来拡張）
- macOS Metal 実装（仕様枠のみ。実装は後続）

## 2. 用語

| 用語 | 意味 |
| ---- | ---- |
| ランタイム | 同梱する `llama-server` バイナリ群と、それを起動・監視する ArkOffice 側モジュール |
| モデルディレクトリ | GGUF を置く既定フォルダ |
| ローカルモード | 自端末でランタイムを起動し `127.0.0.1` に接続する運用 |
| リモートモード | 外部の OpenAI 互換エンドポイントにのみ接続する運用（同梱ランタイムは起動しない） |
| 推論ホスト | リモートモードの接続先、またはローカルで LAN 公開をオプトインした端末 |
| スロット | llama-server の同時処理枠（本仕様では `-np 1`） |

## 3. 運用モード

### 3.1 モード一覧

| モード ID | 名称 | 同梱 llama-server | AI Base URL（既定） |
| --------- | ---- | ----------------- | ------------------- |
| `local` | ローカル | **起動する** | `http://127.0.0.1:8080/v1` |
| `remote` | リモート | **起動しない** | ユーザー入力（例: `http://192.168.10.20:8080/v1`） |

既存の AI プロバイダ `local`（OpenAI 互換）を継続利用する。モードは「どのプロセスが API を提供するか」の制御であり、クラウドプロバイダ（OpenAI 等）とは独立する。

### 3.2 切替 UI

- **初回セットアップウィザード（必須）**と**設定画面（変更可）**の両方を提供する（決定: 3-c）
- 初回: モード選択 →（ローカルならバックエンド／モデル確認）（リモートなら Base URL）→ 接続テスト
- 設定: いつでもモード・URL・バックエンド・モデルを変更可能
- リモート → ローカルへ切替時: ランタイムを起動してから Base URL を loopback に戻す
- ローカル → リモートへ切替時: 同梱ランタイムを停止してからリモート URL を適用する

### 3.3 リモートモード時のランタイム

同梱 `llama-server` は **起動しない**（決定: 4-a）。予備起動は行わない。

### 3.4 Base URL 入力

- **自由入力**（決定: 5-a）。例: `http://192.168.10.20:8080/v1`
- 保存前に URL としてパース可能か検証する（スキームは `http:` / `https:` のみ）
- 末尾の `/v1` 有無は正規化してよい（実装はいずれかに揃える。推奨: 保存時に `/v1` を保証）

## 4. モデルディレクトリと GGUF

### 4.1 既定パス（Windows）

```
%ProgramData%\ArkOffice\models
```

展開例: `C:\ProgramData\ArkOffice\models`（決定: 1-a）

- インストーラまたは初回起動時にディレクトリを作成する（権限不足時はエラー案内）
- 環境変数 `ARKOFFICE_MODELS_DIR` があればそれを優先する（管理者上書き用）

### 4.2 検出ルール

- 拡張子 `.gguf`（大文字小文字無視）を対象とする
- サブディレクトリは **第 1 階層まで**走査する（`models\foo.gguf` および `models\subdir\bar.gguf`）。それより深い階層は対象外
- シンボリックリンクは辿ってよいが、解決先が models 配下以外でもロードは許可する（運用者責任）

### 4.3 既定モデルの選択（複数ある場合）

- **ファイル名のロケール非依存ソート（Unicode コードポイント昇順）で先頭**を既定とする（決定: 2-a）
- ソートキーはファイル名（パスではなく basename）
- ユーザーが設定画面で別モデルを選んだ場合は、その選択を設定に永続化し、次回起動では **明示選択を優先**する（「先頭」は「未選択時の既定」）
- 明示選択モデルが消失した場合: ソート先頭にフォールバックし、設定画面で警告を出す

### 4.4 モデル差し替え手順（運用）

1. ArkOffice を終了する（ローカルモードでロード中の場合）
2. 対象 `.gguf` をモデルディレクトリへコピー／置換／削除する
3. ArkOffice を起動する（または設定から「モデルを再読込」）
4. 必要なら設定でモデルを選び直す

ホットスワップ（起動中のモデル切替）は **必須としない**。対応する場合はランタイム再起動を伴うこと。

## 5. 同梱ランタイムとバックエンド

### 5.1 同梱バイナリ（Windows）

次の **3 系統**を同梱する（決定: 7-a）:

| ID | バックエンド | 想定用途 |
| -- | ------------ | -------- |
| `cuda` | CUDA | GeForce 等の NVIDIA dGPU |
| `vulkan` | Vulkan | 多くの iGPU、および CUDA が使えない GPU |
| `cpu` | CPU | GPU 無し、またはフォールバック |

配置例（インストール先 `resources` 配下）:

```
resources/llm/
  llama-server-cuda.exe
  llama-server-vulkan.exe
  llama-server-cpu.exe
  (必要なら付随 DLL)
```

正確なファイル名はビルドパイプラインで固定し、本仕様の ID と対応表をリリースノートに記載する。

### 5.2 選択方式

**自動検出＋手動上書き**（決定: 6-c）

自動検出の優先順位:

1. NVIDIA GPU かつ CUDA ランタイム／ドライバが利用可能 → `cuda`
2. それ以外で Vulkan 対応 GPU が利用可能 → `vulkan`
3. 上記不可 → `cpu`

手動上書き:

- 設定 UI で `自動` / `CUDA` / `Vulkan` / `CPU` を選択
- `自動` 以外は検出結果を無視して指定バイナリを起動
- 起動失敗時: エラーを表示し、可能なら一段弱いバックエンドへのフォールバックを提案（自動モード時は自動フォールバックしてよい）

### 5.3 起動パラメータ（ローカルモード）

最低限次を付与する:

| 項目 | 値 |
| ---- | -- |
| モデル | 選択中の GGUF 絶対パス（`-m`） |
| ホスト | 既定 `127.0.0.1`（§7 参照） |
| ポート | 既定 `8080`（競合時は設定または空きポート探索。仕様上の既定は 8080） |
| 並列スロット | `-np 1`（§6） |
| GPU レイヤ | バックエンドに応じ `-ngl` を設定（CUDA/Vulkan は可能な限りオフロード。CPU は `0`） |

OpenAI 互換 API が `http://127.0.0.1:8080/v1` で応答することを接続テストの成功条件とする。

### 5.4 プロセス管理

- ArkOffice（shell メインプロセス）が子プロセスとして起動・監視する
- アプリ終了時に子プロセスを終了する
- 異常終了時はログを残し、AI 操作時に再起動を試みる（無限ループ防止の上限あり）
- ポート占有・モデル無し・VRAM 不足はユーザー向け日本語メッセージにする

### 5.5 macOS（後続）

- 本フェーズでは実装しない（決定: 8-c）
- 将来: Metal ビルドの `llama-server` を同梱し、モデルディレクトリは相当する Application Support / 共有パスとする
- Windows 向け設定スキーマは流用し、バックエンド ID に `metal` を追加する

## 6. 順番待ち

### 6.1 サーバ側

- 推論を提供する `llama-server` は **`-np 1`** で起動する（同時推論 1）
- 追加リクエストは llama-server の受付待ちに回る

### 6.2 クライアント／プロキシ側の待ち表示（必須）

決定: 9-b（`-np 1` に加え、待ち人数・順番を表示）

**実装（L5）:** 同梱ランタイムは薄い待ち行列プロキシを公開ポートに立て、`llama-server` は loopback の内部ポート（公開ポート + 10000）のみで待受する。

- ステータス: `GET /arkoffice/queue`（`?id=<X-ArkOffice-Request-Id>` で自分の順番）
- AI パネルはストリーム開始前にポーリングし、「順番待ち（およそ N 件前）」を表示
- キャンセル（abort）でキューから除去
- 既存の接続／アイドルタイムアウトは変更しない

実装方針（いずれか、または併用）:

1. **推論ホスト上の薄い待ち行列プロキシ**（推奨・採用）  
   - ArkOffice 同梱または推論ホスト専用の小さなキューアダプタが、OpenAI 互換 API の前段に立つ  
   - 実際の推論は後ろの `llama-server`（`-np 1`）へ直列化  
   - クライアントはプロキシのステータス（例: 待ち人数、自分の順番、推定不可なら省略可）を取得し UI 表示
2. **llama-server のメトリクス／スロット情報をポーリング**し、UI に「混雑」「順番待ち」を出す  
   - 正確な「自分の順番」が取れない場合は、プロキシ方式へフォールバック

最低限の UX:

- AI パネルに「処理中」「順番待ち（おおよそ N 件前）」などの状態表示
- キャンセル可能（ユーザー中断で HTTP を abort。キューからも除去できること）

### 6.3 タイムアウト

- **既存の AI タイムアウトを維持する**（決定: 10-a）
  - 接続: `AI_CONNECT_TIMEOUT_MS`（現行 60s）
  - アイドル: `AI_IDLE_TIMEOUT_MS`（現行 60s）
  - 非ストリーム応答: `AI_CHAT_RESPONSE_TIMEOUT_MS`（現行 180s）
- 待ち行列が長い場合、接続タイムアウトに達しうる。その場合は「混雑のため時間切れ」を明示し、再試行を促す
- 待ち専用の長タイムアウトは本フェーズでは導入しない（将来: 管理者設定）

## 7. ネットワークとセキュリティ

### 7.1 待受アドレス（決定: 11-b）

| 状況 | バインド |
| ---- | -------- |
| ローカルモード（既定） | `127.0.0.1` のみ |
| 推論サーバ機として LAN 提供 | **明示オプトイン**で `0.0.0.0`（または指定 NIC）を許可 |

オプトイン要件:

- 設定項目（例: 「同一 LAN の他端末からの接続を許可する」）が ON のときのみ非 loopback で待受
- OFF のとき、リモートクライアントは接続できない
- ファイアウォール案内（Windows の受信規則）をドキュメントに記載する
- 認証（API キー）は任意。閉域ではネットワーク分離を主防御とし、キーは空でも可（既存 local 方針と整合）

### 7.2 閉域との整合

- 既定ではインターネット上のホストへの外向き通信を追加しない
- リモートモードの Base URL は管理者が許可したイントラネットに限定する運用とする（アプリ側のホスト許可リストは任意。本フェーズでは必須としない）
- 自動更新・Web 検索の既定 OFF は変更しない

## 8. 設定データ

### 8.1 論理スキーマ（案）

`userData` 配下の設定（既存 `ai-settings` と統合、または隣接ファイル `llm-runtime.json`）:

```json
{
  "runtimeMode": "local",
  "backend": "auto",
  "listenLan": false,
  "port": 8080,
  "modelsDir": null,
  "selectedModelFile": null,
  "remoteBaseUrl": "http://192.168.10.20:8080/v1",
  "providers": {
    "local": {
      "apiKey": "",
      "model": "",
      "baseUrl": "http://127.0.0.1:8080/v1"
    }
  }
}
```

| フィールド | 説明 |
| ---------- | ---- |
| `runtimeMode` | `local` \| `remote` |
| `backend` | `auto` \| `cuda` \| `vulkan` \| `cpu` |
| `listenLan` | `true` のときのみ非 loopback 待受 |
| `port` | ローカル待受ポート |
| `modelsDir` | `null` なら既定 `%ProgramData%\ArkOffice\models` |
| `selectedModelFile` | basename または相対パス。`null` ならソート先頭 |
| `remoteBaseUrl` | リモートモード時に `providers.local.baseUrl` へ反映 |
| `providers.local.*` | 既存 AI 設定と同期 |

### 8.2 環境変数

| 変数 | 用途 |
| ---- | ---- |
| `ARKOFFICE_MODELS_DIR` | モデルディレクトリ上書き |
| `ARKOFFICE_LLM_BACKEND` | `auto` / `cuda` / `vulkan` / `cpu` |
| `ARKOFFICE_LLM_LISTEN_LAN` | `1` で LAN 待受オプトイン（設定より優先してよい） |
| `ARKOFFICE_LLM_DIR` | 同梱 llama-server ディレクトリ上書き（開発・検証用） |

## 11. 受け入れ条件（テスト観点）

| ID | 条件 |
| -- | ---- |
| AC-1 | モデルディレクトリに 1 つの GGUF のみがあるとき、ローカルモードで AI が一通り動作する |
| AC-2 | 複数 GGUF があるとき、未選択ならファイル名ソート先頭がロードされる |
| AC-3 | リモートモードでは同梱 `llama-server` プロセスが存在しない |
| AC-4 | リモート Base URL を自由入力し、推論ホストへ接続できる |
| AC-5 | バックエンドを `auto` / 手動の各値に切り替え、対応環境で起動できる（非対応は明確なエラー） |
| AC-6 | CUDA・Vulkan・CPU の 3 バイナリがパッケージに含まれる |
| AC-7 | `-np 1` 運用下で 2 クライアント同時リクエスト時、後発が待ち状態を UI で認識できる |
| AC-8 | ローカル既定は `127.0.0.1` のみ。LAN オプトイン OFF では他端末から接続できない |
| AC-9 | LAN オプトイン ON の推論ホストに、他端末がリモートモードで接続できる |
| AC-10 | タイムアウト値は既存 AI ウォッチドッグと同一である |
| AC-11 | 初回ウィザードと設定画面の両方からモード変更できる |
